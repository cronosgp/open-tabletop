# Army Builder and ForceOrg data flow

This note records the implementation boundaries audited for the Army Builder and ForceOrg visual variants plan. Army lists, accepted match rosters, gameplay state and local appearance data are related, but they are not the same record.

## Ownership and data flow

| Stage | Code owner | Responsibility |
|---|---|---|
| Construction catalog | `scripts/implemented_army_catalog.gd` | Expose the consolidated local runtime catalog. Runtime construction uses `scripts/implemented_army_catalog.gd`; `scripts/army_catalog.gd` has been removed and is no longer part of the runtime path. Construction does not fall back to the broad OpenHammer API catalog. |
| Saved profile and list | `scripts/army_profiles.gd`, `scripts/army_roster.gd` | Read/write local profiles; validate list shape, model identities, supported equipment, formation candidates and local visual references. Migrate older flat visual slots in memory. |
| Army Workshop | `scripts/army_builder_panel.gd` | Edit composition, supported per-model equipment, saved formation candidates and local appearances. Keep unsaved drafts in the session and save them only when requested. |
| Rules admission | `scripts/edition_11/army_capabilities.gd`, `scripts/edition_11/training_roster.gd` | Revalidate saved selections against current local source-bounded capabilities and produce canonical roster configuration. Unsupported or pending-validation choices remain blocked. |
| Match materialization | `scripts/edition_11/prepared_training.gd`, `scripts/edition_11/unit_actions.gd` | Create deterministic gameplay units from canonical selections, apply supported saved equipment and formation declarations, and retain match-specific declarations for choices not stored by the builder. |
| Local appearance | `scripts/visual_resolver.gd`, `scripts/model_import_panel.gd`, `scripts/main.gd` | Resolve renderable model overrides, equipment/role candidates, shared appearance and built-in fallback. Record rationale and warnings. Asset availability does not alter rules state. |
| Match persistence and LAN | `scripts/match_save.gd`, `scripts/main.gd` | Save authoritative match state. Keep local appearance snapshots in the presentation section; strip local paths and model identities from gameplay roster projection. |

The normal path is:

```text
Saved ArmyProfile
  → current local catalog admission
  → canonical roster with supported equipment
  → PreparedTraining match state
  → gameplay snapshot

Saved local appearance references
  → separate match presentation snapshot
  → local VisualResolver
  → prepared asset or built-in fallback
```

## Identity and compatibility

- Each unit copy has a stable local ID; each model ID derives from that copy ID and model slot. Reordering canonical configurations therefore does not reassign the source model's saved appearance.
- Supported model equipment is keyed by stable model ID in `model_equipment_by_id`; Reiver squad gear remains keyed by stable copy ID in `unit_equipment_by_copy_id`. Aggressor packages are per miniature and older preview records migrate from copy-level equipment. Indomitor's role-shaped defaults and validators distinguish three Aggressors, three Eradicators and four Heavy Intercessors. The saved-list path also includes Scout model loadouts, Reiver Grav-chutes and Grapnel Launchers, Intercessors, Assault Intercessor Sergeant weapons, Heavy Intercessor Heavy Bolters, Eliminators, Outriders, Ravenwing Darkshroud, Ravenwing Black Knights and Command Squad Grenade Launchers, Land Speeder, Land Speeder Vengeance, Baal Predator packages, Predator Destructor and Predator Annihilator packages, Hellblaster Sergeant pistols, Inceptors, Invader ATV Multi-meltas and the Necron profiles listed in the Army Builder guide. `army_roster.gd` deliberately allowlists fields by datasheet; this is not yet a catalog-wide loadout schema.
- Per-model sculpt overrides and Auto/Manual selection modes are keyed by the same stable model ID. A non-empty saved override means Manual, even if its local asset is missing; Auto follows the resolver. Older profile files infer the mode from their override and are normalized on load/save.
- Unit-copy appearance, per-model override and army palette are local presentation references. They do not enter points, legality, weapon records or dice resolution.
- Sword Brethren uses `sword_brethren_loadout` per stable model/copy; the existing `sword-brethren-loadout` match-preparation command remains for unsaved fixtures and is suppressed/rejected when saved equipment is locked.
- Match appearance snapshots use schema v3 for explicit model modes. The reader retains schema v1 unbound and schema v2 copy-bound compatibility. Snapshot validation checks each stable copy/model identity and, for bound snapshots, its frozen canonical unit index.
- Prepared GLB packages cache a `PackedScene` and instantiate a separate scene tree for each miniature. The mesh resources are shared while scene nodes and per-model transforms remain independent; the local GLB regression checks that boundary.
- For supported model roles, the gallery recomputes equipment/role rationale from the saved loadout and local mapping metadata. A conflicting manual sculpt remains selected and is labelled for review; candidates without enough metadata remain explicitly unverified. The focused Army Builder regression checks a Hellblaster Sergeant pistol conflict and its update when the saved pistol changes back.
- The Appearance tab keeps the live preview/model selector beside the local gallery and orders selectable looks before optional preparation and palette actions. Below 1560 logical pixels, the outer three-region Workshop changes to compact navigation; opening an entry's Appearance view selects the inspector. A focused 1280×800 capture and builder check cover this path, not smaller devices or every viewport width.
- Local saved Warlord/attachment candidates are mapped to the accepted match roster and replayed through current rules choices. LAN roster packets now carry only bounded canonical model/unit coordinates for saved formation candidates; the host revalidates them through the same public rules choices before applying them. The client compares the host's frozen declaration with what it submitted. Stable Army Builder IDs, visual references and local files remain off the wire. Separate-machine LAN validation remains open.
- Missing or failed visual assets preserve the saved ID and fall through the local visual cascade: compatible role/equipment candidates, the saved unit and palette looks, same-family automatic variants, the datasheet's local default mapping, then the built-in miniature. Asset fallback does not change gameplay data. The gallery and match review report current local readiness for explicit appearances; automatic equipment/role candidates are checked during launch preparation. Unavailable saved manual, unit and palette appearances retain resolver warnings plus per-candidate availability and failure reasons. The renderer includes candidate availability in its cache key, so a prepared or repaired asset is retried even when its stable ID is unchanged. Corrupt highest-ranked equipment files fall through to another renderable local variant; failed downloads and invalid OBJ files do not damage earlier links. A focused offline regression covers failed-cache retry, URL-error preservation, and successful recovery after a saved appearance becomes locally renderable. Default-mapping recovery, separate-machine asset behavior and broader import/conversion recovery remain open.

## Migration and implementation risks

1. Older Army Builder profiles use a schema-v1 bank with optional fields. New per-model fields must remain optional on read, validate before use, and normalize only after stable IDs are established. Invalid files are preserved rather than overwritten.
2. Match setup still exposes many source-bounded equipment commands through `UnitActions`. Only a subset has explicit Army Builder fields, admission validation and deterministic materialization. These remaining choices must be migrated profile by profile; a generic UI must not infer legality from display labels or visual metadata.
3. UnitActions model and squad integers are match-local. Persisted choices must bind to saved stable identities, then remap only after admission; raw match indices must not be stored in army profiles.
4. Match snapshots are immutable with respect to later source-list edits. Any new saved configuration must enter canonical admission and the frozen match state before deployment, not read a live profile during play.
5. Visual files and ForceOrg identifiers remain local. Distinct caches across LAN peers, missing upstream assets, unsupported animation and redistribution rights are not solved by roster synchronization.
6. The current catalog and capability records are intentionally partial. Passing a local admission path or test does not certify full army legality, every datasheet option, or a complete official match.

Squad-wide caps and mixed model roles require their own source-specific validation. Existing profile-specific save fields and readers remain supported.
