# Saving and resuming matches

Local matches and LAN hosts can save and resume matches. There are five local slots, separate from army lists and player profiles. Slot 1 retains the existing `user://matches/current.save` path; Slots 2–5 use `user://matches/slots/slot-02.save` through `slot-05.save`. Each slot has its own event-journal directory. The title screen opens the slot browser when there are multiple saves or the only save is outside Slot 1; the in-match **Save match to slot** action opens the same browser in save mode.

The host and local play autosave accepted state updates to the active slot. The save browser identifies the active autosave slot. A fresh local match or LAN host uses the first empty slot, preserving existing saves; if all five are occupied, snapshot autosave pauses and the match is not resumable until the player saves to an empty slot or confirms replacing an occupied one. A slot with only a recoverable backup still counts as occupied. Its event journal continues recording history in an isolated local directory, but the journal alone cannot resume the match; manual saving copies it together with the snapshot. A damaged save file also counts as occupied until the player explicitly replaces it. Manual saving lets the player select any slot; overwriting an occupied slot requires confirmation. After a manual save, that slot becomes active for subsequent autosaves. When a match is copied to another slot, its committed journal is copied under a fresh storage identity before the new save is written, so later play in either slot cannot alter the other's history. The LAN army selection must be complete before saving. A guest never writes over the host's match.

Snapshots preserve native data types, integer model IDs, deployment, positions, casualties, score, pending decisions and the 64-bit random-number-generator state. New writes also record the priority player for the next decision. The slot summary distinguishes the active turn player from a different pending decision owner, for example “Player 1's turn · Player 2 decides.” Older saves without this optional field still show the active player. The attack draft is also included in a manual save. Loading does not execute commands again or roll dice again. Match configuration and local rules-pack identities are checked before the game state is replaced. Truncated files and checksum mismatches are rejected. Save encoding rejects non-finite scalar numbers, vector/rectangle coordinates, color channels and packed floating-point entries. Before replacing a readable primary snapshot, the game copies it to an adjacent `.bak` file. If the primary is missing, corrupt or fails a load-time structural check for saved configuration types, match-state sections, saved-army setup shape, attack-draft fields and references, pending decisions, required state fields, seat reservations or journal references, loading checks that backup; the slot browser labels a recovered snapshot when file-level reading selects it, and a successful load or compatibility check reports when a later structural check selected it. The normal rules, configuration, state and journal checks still run. A primary save from a newer game version remains an explicit compatibility blocker and does not fall back to older state. When fallback is attempted and the backup also fails, the interface reports both errors. The versioned format is limited to 16 MiB, does not deserialize objects and writes the new snapshot through a temporary file before renaming.

To continue over LAN after closing the host, load the desired slot and choose **Resume last match as LAN host** in the recovery controls. The guest selects the same exercise or compatible army list and uses Join to receive the restored state. On first entry, the host reserves a seat and the guest stores a credential in `user://matches/guest-seats.save`. Later, Join proves possession with HMAC-SHA256 and a fresh random challenge before receiving snapshots or sending accepted commands. When the host resumes, the seat reservation comes from the selected save; a guest without the credential or with an invalid proof is rejected. The guest must use the same computer and Godot user data as before. Army-builder profiles are not authentication accounts and use this local storage. Saves from other players remain untrusted: the checksum detects accidental corruption but does not authenticate authorship.

Limits: five local slots, no visual replay or migration across incompatible game versions. Bounded journal compaction is implemented; focused compaction and cleanup verification is pending. Autosave covers published commands; changes only in an attack draft require manual saving. The [persistent event and dice history](match-history.md) records changes and results and checks its saved checkpoint before resuming. Autosave errors are shown in the interface and do not undo an accepted command. Separate-machine LAN resumption still needs validation. The five-slot browser and per-slot journal copying have not yet had focused local verification.

## Reserved LAN seat

Session identity and the token live in a private save section outside the public state sent to players. The first credential is delivered during the guest's initial connection and confirmed only after the guest has saved it and proved possession. The host persists the reservation before accepting commands when the match is saveable. An incomplete army selection cannot be resumed after a restart. Each proof attempt expires after ten seconds. Replaying a prior challenge does not authorize another connection. A failed save prevents admission and leaves the match state unchanged.

This protects a reserved seat from guests without its credential. It does not encrypt ENet traffic, provide online accounts or authenticate the server's identity. The first connection should use a trusted LAN. The interface cannot transfer or reset a guest credential; losing its file prevents automatic recovery. Older saves without a reservation remain loadable and reserve the seat for the first guest in the new session. Restarting an exercise or choosing Host LAN starts a new session; load the existing slot to continue its session.

Each save references an independent journal file. Keep the save and its matching journal together when copying a match. See [match history](match-history.md) for interrupted-write recovery, navigation and limits.
