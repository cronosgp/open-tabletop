# ForceOrg / Tabletop Simulator visual import assessment

Updated 2026-10-31. Automatic catalog/model preparation is implemented for local matches; the manual runtime importer remains available in **Models / Import**. It reads local TTS/ForceOrg saves, previews OBJ meshes and supported child-mesh assemblies, converts a bounded static Unity AssetBundle subset through an optional local helper, saves visual mappings by unit definition and renders them on the board. No third-party models or converter binaries are bundled. Broader ForceOrg library discovery remains incomplete.

Real-content validation is now complete for three sample meshes: two Intercessors and one Necron child component. The current official save's static `objectJSONs` catalogs and `ChildObjects` are discoverable without executing Lua. Model-name search shows at most 200 matches while retaining original source identities. Image decoding uses PNG/JPEG/WebP signatures, so extensionless or mislabeled cached images work. See [real validation results and remaining limits](model-import-validation.md).

## Use the initial importer

### Automatic models for a local match

On first launch, a one-time prompt lets the player choose a local `ForceOrg.json` catalog or continue without automatic model downloads. A selected, validated catalog path is saved in local settings. In **Match setup → LOCAL MATCH • TWO ARMIES**, choose two default/profile lists and use **Create local match with these two lists**. Choosing the catalog in the first-run prompt enables automatic download/linking; that preference is saved across launches and can be changed in New match settings. Choosing **Continue without models** leaves downloads off for other local matches; starting tactical training enables downloads for its six unit types. The game downloads only compatible model files needed by the selected armies; the catalog is not a bulk download of every ForceOrg asset. If downloads are enabled but no source is configured or detected, the game downloads the public ForceOrg JSON automatically, validates its catalog and saves it as `user://ForceOrg.json`, then continues with the miniatures. You can also choose a JSON in **Models / Import → Browse / Scan local save** and use **Retry automatic models for current match**. The game detects `ForceOrg.json` in its user-data directory, project root or the standard TTS Saves directory. The default endpoint is the manual JSON download documented by the [ForceOrg Downloader project](https://gitlab.com/forceorg1/ForceOrg-Downloader/-/raw/main/README.md). Catalog transfers are limited to 64 MiB, three redirects and 60 seconds; invalid/empty JSON or HTTP errors preserve earlier files and report how to retry or select a local source.

Existing valid links are reused, including manual choices. Missing or invalid links for supported unit profiles are queued for repair and replaced only after downloaded files pass validation; failures retain the previous mapping and appear in match status. For unmapped playable profiles, the importer selects a compatible visual variant from the catalog using unit aliases, prefers exact names and sorts equivalent variants by asset URLs. It reports the chosen variant; use Models / Import to override it. Asset URL pairs are deduplicated. This changes appearance only, never roster identity, weapons, bases or rules.

The batch checks downloaded files and the configured cache before HTTP, captures each target definition independently of the selected pawn, validates OBJ/diffuse content and atomically persists each successful link. Successful models appear on all corresponding pawns immediately. Progress, cancellation, errors and retry are available; unavailable models keep placeholders and the match remains playable. No user library lists are created implicitly.

Automatic matching uses exact/model-token names and reviewed visual aliases; it does not infer rules from sculpt names. When a ForceOrg profile is a static composite, the importer downloads each compatible OBJ/diffuse component, preserves the scanned child transforms, assembles the parts, and places the assembly on the game's rules-controlled base. If a matched visual variant fails download or validation, the batch tries the next compatible variant before leaving a placeholder. Asset URLs are deduplicated. This changes appearance only, never roster identity, weapons, bases or rules.

A local visual audit tested all 161 current Space Marine profiles on each side of a Godot table (322 positions, one representative miniature per datasheet). All 161 profiles loaded with no placeholders or download/import failures. For the 24 definitions that lacked a safe automatic exact-name OBJ match, reviewed visual aliases selected an available sculpt from the same miniature category; those links are appearance substitutes and do not claim to be the exact named sculpt. Detected base rings for 153 profiles fit within 0.5 mm; eight models used height/hull normalization. The importer also rejected a malformed, over-wide Judiciar mesh and successfully linked another local variant. This test does not certify rules, every sculpt's pose/height, or full army legality. See the [audit results and limitations](model-import-validation.md).

The static AssetBundle helper was additionally exercised against every bundle component referenced by those 161 profile plans: all 45 unique bundle URLs (406 mesh parts across 42 profiles) passed conversion and Godot validation. The seven Judiciar bundles that referenced external CAB materials now load their matching secondary bundles; all seven reconverted without missing-material warnings. An automatic repair check replaced an old Judiciar link with unresolved CAB warnings and finished with all 10 parts ready. The Invictor and Wulfen meshes fit the bounded 1,000,000-attribute/triangle-vertex OBJ parser. Rhino's 167 texture files contained 37 unique images; 130 duplicates were hard-linked, keeping its 57-part conversion below the 256 MiB unique-output limit. These are local static-model checks; the 161-position table itself used compatible OBJ links and the reviewed visual aliases above.

### Manual direct download

Open the JSON, search/select a miniature or supported composite, choose the download folder and press the selected-model download button. Default destination is `user://downloaded-models`. Scanning/searching alone does not download assets. The manual path opens a preview and requires saving its association; the automatic batch above links validated files directly.

Transfers require HTTPS, allow at most three redirects, time out after 45 seconds per file and are limited to 64 MiB per file. Files are validated before becoming permanent; versioned filenames preserve older content. Manual selection changes prevent a stale download from being previewed as another object. Unity bundles require the optional local converter at `user://forceorg-converter/forceorg-bundle-converter.exe` on Windows. It converts supported static renderers to bounded OBJ/MTL/image assemblies, preserves scanned transforms, and never executes Lua or bundle scripts. Animated content, arbitrary Unity bundles and bundles exceeding the conversion limits remain unavailable with a per-model error.

### Existing files / TTS cache — optional

1. Independently acquire ForceOrg and the desired models using the user's existing workflow. The downloader installs the utility save; it does not itself install all referenced model meshes.
2. Start an exercise and select a model in **Play** to identify the target unit definition.
3. Open **Models / Import**. Choose `ForceOrg.json` or a TTS saved army/object JSON and press **Scan local save**. The source path also accepts a directory containing `ForceOrg.json`. Search model names and choose an entry to inspect original references/credits. Static JSON literals in the known `objectJSONs` table and child components are included; Lua and remote references are never executed or fetched. Components without a name inherit their parent's searchable name.
4. Choose your **Local TTS Mods / cache folder** and press **Find selected object's local files**. The importer searches that directory and its subdirectories for full-URL-derived alphanumeric filenames, with optional OBJ/image extensions. A unique mesh and any declared diffuse texture load the preview automatically. Missing or ambiguous matches are reported beside the lookup button; select those files manually instead. No network requests occur. **Save cache folder setting** persists the chosen folder. This adapter recognizes specific filename conventions, not every possible TTS/cache version.
5. Alternatively, choose a locally downloaded OBJ (extensionless cached text OBJ is accepted) and optional diffuse PNG/JPEG/WebP, then press **Load model preview**.
6. Adjust extra visual scale, rotation and height. When an OBJ includes a round miniature base, the importer measures and centers its lower base ring, then matches that base to the in-game base; weapons and staves do not affect its scale or placement. If the OBJ has no detectable base, infantry on bases up to 43 mm use a 1.35 height-to-base ratio, while larger sculpts use their horizontal footprint. ForceOrg `Transform.scale` is used only when the unit base radius is unavailable and the mesh already looks inch-scaled. Imported models face the board centre with a half-turn correction for the current ForceOrg OBJ set; ForceOrg's saved rotation is a tabletop pose, not a reliable catalog-wide facing reference. Use the rotation control for an OBJ whose authored front uses another axis. These are visual adjustments only and do not change gameplay bases. Press **Save visual for selected unit type**. All models sharing that definition use this local visual. Different sculpt variants per model remain future work.
7. Use **Remove visual for selected unit type** to restore placeholders. Mappings and the cache folder persist in `user://local-models.cfg` and reference source files without modifying them. Missing or changed mesh/texture files fall back to placeholders when loaded again; preview and save again to accept replacements. Already loaded meshes remain cached for the current run.

Supported: text OBJ triangles and convex polygon faces, including faces with more than 64 vertices, bounded at 1,000,000 source attributes and 1,000,000 triangulated vertices; negative indices, optional UVs, recomputed normals, vertex colors, MTL multiple materials, diffuse and normal maps, per-component textures, scanned `ChildObjects` mesh assemblies with local transforms, and a bounded static Unity AssetBundle conversion subset. Static bundle conversion extracts enabled mesh renderers, texture/material references and transform chains, matches secondary bundles only to dependency names declared by the primary bundle, normalizes safe OBJ paths, validates every part and records texture/UV limitations. Each bundle input is limited to 64 MiB; up to 16 dependencies are supported with a combined input cap of 128 MiB. Identical imported image contents reuse a shared in-memory texture while the converter hard-links duplicate image files where the output filesystem supports it. A flat renderer may be included when the overall composite has usable geometry; maps are omitted with a warning when its OBJ has no UV coordinates. The bounded local cache lookup uses full URL-derived names. It ignores hidden entries and symbolic links, does not match by short asset ID/basename alone, recognizes the `{verifycache}` URL prefix, and selects a converted bundle only when its material-dependency fingerprint matches. It re-indexes on each explicit lookup so newly cached files and duplicates are visible. Bounds: eight subdirectory levels, 2,048 directories and 50,000 files; exceeding a bound fails the scan instead of using partial results. Unsupported/hashed cache naming still requires manual selection.

Not yet supported: animated pose playback, arbitrary/dynamic Unity AssetBundles, GLB imports or arbitrary dynamically computed Lua catalogs. A ForceOrg composite is unavailable if any required part is unsupported or lacks a usable mesh. Static bundles can contain imperfect geometry or omit UVs; the converter reports those cases, recomputes normals and drops texture maps that cannot be applied. The 161-profile visual audit uses reviewed visual aliases for 24 profiles; those links are appearance substitutes and do not certify an exact named sculpt. Infantry meshes without a detected base ring are rejected when height-normalized geometry would exceed 3.5 base diameters in width. Known static `objectJSONs` long-string JSON tables are parsed as data, including equal-sign delimiters; expressions or malformed tables are skipped with warnings. OBJ source attributes and triangulated vertices are each bounded at 1,000,000; save/mesh files and total extracted static JSON at 64 MiB; scanned object records at 100,000; textures at 8192 pixels per side and 64 MiB per file. Static bundle conversion is bounded to 64 MiB per bundle input, 16 dependencies, 128 MiB combined input, 256 MiB of unique on-disk output, 2,048 files, 256 rendered parts and 100,000 serialized objects. Concave polygon triangulation is not guaranteed; triangulate such models before import.

Earlier synthetic validation covered parsing, cache ambiguity, persistence, state isolation and placeholder fallbacks. Real-content results, including the full 161-profile visual audit and the remaining import limits, are in the [validation report](model-import-validation.md). Downloaded model files and rendered captures remain local in ignored `.tools`/user-cache directories and are not shipped.

## Confirmed acquisition workflow

The intended catalog source is ForceOrg itself (Workshop item 3753014527 and ForceOrg-Downloader). The user subsequently requested an in-game per-model download option to remove the dependency on TTS/cache. The game supplies the importer and explicit download control; it does not ship the collection, run its external downloader, subscribe to Workshop items, acquire the whole library or transfer assets to other players. Existing local files/caches remain optional inputs. Original files are preserved and downloads stay in a local player-selected library.

Primary sources:
- https://steamcommunity.com/sharedfiles/filedetails/?id=3753014527
- https://gitlab.com/forceorg1/ForceOrg-Downloader

The downloader's public README and DownloaderUI.cs were subsequently inspected. It writes `ForceOrg.json` and `ForceOrg.png` into the selected TTS Saves directory. Its code does not download the full mesh/texture collection. The mesh files still need to exist locally, for example from the player's TTS workflow. No downloader executable was run. The backup inspection below is supporting evidence about one TTS save, not a specification of a complete ForceOrg collection.

Implementation must prioritize reading the formats actually produced by the player's ForceOrg download. Where a downloaded format needs conversion, provide a supported local adapter or a precise per-file unsupported status. Do not promise conversion of arbitrary AssetBundles.

## Backup findings

Source: https://github.com/KMill-source/TTS-Resources-Backup

The repository describes itself as a backup of TTS table saves. Its ForceOrg directory contains TS_Save_1.json and a preview PNG, not a standalone catalog of miniature meshes. The downloaded JSON identifies itself as ForceOrg 6-29-2026 and is approximately 43 MB. An inspection of ObjectStates, recursively including ContainedObjects and alternate States, found 140 root objects and 3,245 total object records, including 56 CustomMesh and 4 CustomAssetbundle records. These counts describe those fields in this save, not unique miniature assets or a complete ForceOrg library. Many sampled mesh records are bases or utility objects. Models loaded by scripts or external services require separate discovery; the importer must not assume the table save contains the player's army.

CustomMesh records hold MeshURL, DiffuseURL, NormalURL and ColliderURL references. Referenced files are external dependencies and their availability/content has not been verified. CustomAssetbundle records hold AssetbundleURL references. No asset meshes, textures or bundles were downloaded or redistributed during this assessment, and no source Lua or installer scripts were executed.

The repository LICENSE explicitly reserves save content to the respective creators and says the maintainer has no licensing rights over it. The public-domain permission applies to the maintainer's installer and documentation. Therefore this repository does not establish permission to bundle these models in our distribution. Track creator, origin, attribution and applicable permission per asset; local import support itself does not establish rights to copy or distribute content.

## Planned player configuration

Add a dedicated **Models / Import** area under Match setup, independent of combat setup and the future battlefield builder:

1. Choose the local ForceOrg download/output directory. Optionally select a local TTS saved-object JSON or table-save JSON and asset/cache directory when the downloaded collection needs them. Detect the actual layout and report what was found; the ForceOrg utility-table save alone is not assumed to contain the collection.
2. Scan references without executing Lua, downloading files or modifying the army. List objects by name and stable source identity, distinguish contained objects and alternate states, and report missing/unsupported references. Deduplicate referenced files without collapsing distinct instances or variants.
3. Select candidate miniature assets and explicitly map them to our faction/unit/model identifiers. Names may suggest matches but must not silently grant stats, equipment, abilities, roster legality or base sizes.
4. Preview the visual model with configurable scale, rotation and vertical offset. OBJ/MTL/images and the supported static Unity bundle subset are imported locally. The optional converter is installed or built by the player; model content and converter binaries remain outside the distributed game.
5. Persist versioned local mappings and settings, including provenance and fingerprints. Never execute embedded scripts or adopt source colliders. Keep gameplay bases, selection markers and authoritative geometry controlled by our rules/scenario data. Visual imports do not make mesh-based visibility or vertical geometry supported.
6. Missing or incompatible assets fall back to the existing placeholder with a clear status. In multiplayer, share the logical identity only; each player supplies local visuals or explicitly downloads the chosen model. Automatic inter-player asset transfer remains a future feature.

Initial local completion criteria are met using original OBJ/cache fixtures: scan a saved object, locate uniquely matched cached files, preview and map its mesh, persist/reload, render on the board and return placeholders for missing/unmapped visuals without changing gameplay state. Real miniature and automatic catalog/download validation has since passed; see [latest results](model-import-validation.md). Remaining acceptance work includes separate-client validation and additional format/composite adapters.

Implemented: catalog discovery, supported OBJ/MTL/image adapters, static composite and supported bundle assembly with preserved local transforms, preview/mapping/persistence, board integration/fallback, explicit per-model downloads and match-scoped automatic downloads with compatible-variant retry. Bundle conversion requires the optional local helper and handles no script content. The game fetches only visuals needed by the selected profiles, not the whole collection. This visual feature does not control rules geometry and is distinct from the deferred battlefield editor. Core rules and current UI clarity work remain active roadmap items.

## Identifying catalog entries

The picker now shows miniature names instead of CustomMesh/internal object paths. Repeated names have numbered options, named millimeter bases are marked Base, and child components are labeled Peça. A visible selected-entry description explains separate components; verify the preview before applying. Missing local references explain that a JSON save is a catalog, not a download of the model/texture, and that the project/save directory may not be the cache directory. Source URLs, credits and paths remain in the detailed notice. Three related local suites passed for this usability correction.
