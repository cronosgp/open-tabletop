# Real ForceOrg import validation

Validated 2026-10-15 on Windows with Godot 4.7.2. The user explicitly authorized downloading/installing ForceOrg as necessary to test real model imports. No TTS cache was found in the standard Documents/OneDrive paths, and TTS was absent from the inspected standard Steam library. Installing TTS or running the downloader EXE was unnecessary: the official downloader documents a manual save download, which was used directly.

## Test data and provenance

- Official save: https://forceorg-download.raikoh.workers.dev/ForceOrg.json
- Manual workflow: https://gitlab.com/forceorg1/ForceOrg-Downloader/-/raw/main/README.md
- Local save size: 43,290,282 bytes; embedded SaveName: `ForceOrg 5`.
- SHA-256: `ED0B66DC0518F03EA746A485D2739DEB57EA2094117D552C02925983C3BCBA44`.
- Latest scanner output: 35,936 object records, 32,256 mesh/bundle entries, 10,605 static embedded objects, zero skipped-table warnings. These are entries/parts/variants, not unique complete miniatures.

Three meshes and two shared/distinct texture files were downloaded from the save's own Steam content references. Meshes tested: **Primaris Intercessor Sgt**, **Primaris Intercessor**, and **necron warrior reaper / component 1**. Marine mesh sizes were 332,864 and 331,780 bytes; the Necron component was 1,101,919 bytes. Marine diffuse image: 1536 pixels wide, 1,904,017 bytes; Necron diffuse image: 2048 pixels wide, 1,547,689 bytes. Credits/source descriptions are retained in catalog entries and local mapping metadata. Source save, manifests, downloads, logs and screenshots remain in `.tools/forceorg-real`, ignored by Git and excluded from the distributed project content.

## Defects found and corrected

1. The original scanner saw mostly table/base objects. Added a bounded parser for JSON long-string literals in ForceOrg's `objectJSONs` tables. It does not execute Lua; computed expressions are rejected and warnings are shown.
2. Actual miniature components can live in `ChildObjects`, while the parent mesh is only a base. Added child traversal, inherited names/credits and explicit component identities. Components can be selected individually; automatic composite reconstruction is still unsupported.
3. Once these records were expanded, the real collection exceeded the previous 20,000-record limit. Raised the bounded object limit to 100,000 while retaining file/extracted-data byte limits.
4. The expanded catalog needs search. Added model-name filtering, capped displayed matches at 200 and preserved original entry indices/identity after filtering.
5. A real texture was JPEG content saved under a `.png` cache name. Replaced extension-based image loading with PNG/JPEG/WebP content detection, also supporting extensionless image files.

## Passed checks

- Real save scan and name-based selection, including static catalogs and child components.
- Unique local URL-derived cache matching, OBJ parsing and texture decoding for all three samples.
- Preview rendering, application to the unit definition and actual board rendering; match state remains unchanged by visual mappings.
- Save/reload of Marine and Necron mappings; a fresh main-scene launch automatically displays both imported unit types.
- Six portable local suites: static ForceOrg catalog, local models, cache lookup, allocation practice, gameplay layout and guided attacks.
- One host/client loopback allocation scenario with disconnect/rejoin while the actual local model profile was available.
- Graphical preview and board screenshots visually inspected at 1280x800.

The local default game profile (`user://local-models.cfg`) now references the tested Marine/Necron files and cache folder. Any existing profile would be copied into the local test directory before replacement; none existed on the first installation. Practice exercises use these visuals on the next ordinary launch. Local files must remain available, or placeholders will be used. Visual weapon/sculpt choice is independent of the practice army's equipped weapon rules.

## Limits

This proves the tested OBJ/image path for three samples, not every entry in ForceOrg. AssetBundles, full composite assembly/transform fidelity, MTL/multiple materials, normal maps, vertex-color-only appearance and arbitrary dynamic Lua remain unsupported. The cache was assembled from the save references for this test; it was not generated by running TTS, so other actual TTS cache conventions still need testing. Linux and separate-machine networking remain unverified. No automatic downloading, installer execution or third-party asset transfer was added to the game.


## Automatic first-run validation — 16 October 2026

An isolated empty user profile started the two-default-list local match with no configured JSON or cache. The game downloaded the public ForceOrg catalog, selected Primaris Intercessor and the previously verified Necron Warrior body, fetched both mesh/diffuse pairs, saved the links and rendered both army types during deployment. `.tools/qa_forceorg_end_to_end.log` reports `Models ready: 2/2`; `.tools/forceorg-end-to-end-downloads` contains two OBJ files (331,780 and 1,101,919 bytes) and two diffuse images (840,704 and 1,547,689 bytes). The official JSON endpoint was confirmed against the ForceOrg Downloader README linked above.

Earlier runs in this increment tested a configured source with external cache reuse and a fresh model-download folder without cache. Visual QA at 1280 × 800 covered the primary two-list setup action and the deployment board with both real models. Captures: `.tools/local-match-setup.png` and `.tools/local-match-models.png`. Catalogs, models, profiles and captures are local verification artifacts, not bundled assets.

The Necron body is a deliberately supported known component, not generic composite reconstruction. Other unsupported parts retain placeholders/manual resolution. Automatic visuals never alter gameplay state or unit definitions.
